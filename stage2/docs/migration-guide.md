# 迁移与回归说明

执行前提：SQL Server 已启动，ODBC Driver 18、Python 与依赖可用；配置阶段 Windows 账户有建库、备份、还原及授予应用角色的权限。日常应用不使用这些有效权限。

1. 保留 v0.1 原库。默认 setup 对 MilkTeaShopV01 做唯一文件名 COPY_ONLY/CHECKSUM 完整备份并还原为全新目标库，目标存在直接拒绝。原库和备份均保留。也可 --from-scripts 从仓库 sql/01、02、09、05 创建独立 v0.1 基线，供空环境复现。
2. 在目标副本上执行 sql/migration.sql：检查六表和订单基线、重复明细与空订单；持久化 Baseline_* 迁移前快照；增加 AppUser、两个过滤唯一索引、SchemaVersion；增加订单来源及扣库标志，允许草稿暂无员工，扩充状态并将默认值改为 DRAFT。整份迁移用一个事务和 XACT_ABORT，任一步失败回滚。
3. 执行 sql/application.sql，更新订单详情视图使无员工草稿可见，创建订单过程和四个最小授权数据库角色。setup 再创建随机密码的应用角色，复制对应授权，装载四个哈希应用账号。
4. 执行 sql/regression.sql：双向 EXCEPT 比较订单明细、商品销量和库存；关键标识和销售金额验证；合法写入、非法外码/负库存、当前价与历史价独立验证；店员权限正反例。结果保存 result/regression.txt。
5. AppUser 在配置后有四行；SchemaVersion 一行；基线快照各自对应原表/视图行数。这些新增行不是业务丢失或重复。六个原业务表仍为 6/6/4/3/7/11 行，完成 6 单、15 杯、86.00 元。历史订单 StockApplied=0，不按历史销量重新扣减开库库存。

冲突策略：不盲目合并重复标识、不自动补空订单。遇到基线不符合预期则抛错并保留副本与原库，先核查数据。脚本不要求可重复执行；SchemaVersion 已存在将拒绝重跑。配置后半段失败时保留失败副本，修复原因后换一个新目标库名重做，不使用删库掩盖迁移问题。

恢复：迁移事务失败自动回滚；应用操作失败由 DAO rollback。若迁移已提交后需要退回，停止应用并指回保留的 v0.1 数据库或独立还原备份；v1.0 新增订单须另存，不能宣称降级能保留尚未转换的新数据。初始化脚本从不删除原库或目标库。

类别异常演示由 normalization_demo.sql 独立临时表完成，不改变六张业务表。
